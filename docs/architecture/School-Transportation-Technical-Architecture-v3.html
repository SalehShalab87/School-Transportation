1. Executive Architecture Summary

The solution uses a single-school deployment model with one isolated database, a modular monolith for transactional business capabilities, and a separate Worker host for long-running planning jobs and durable background delivery. The design keeps deployment simple while preserving strict module ownership and Clean Architecture dependency direction.

  • ASP.NET Core API is the operational entry point for administrative, mobile, integration-webhook, and real-time use cases.
  • Business modules are organized as module folders inside shared Domain, Application, and Infrastructure projects. API and Worker are thin hosts.
  • The Planning module owns planning use cases and persistence abstractions; the Worker hosts long-running Planning application use cases rather than bypassing module boundaries.
  • PostgreSQL is the transactional system of record and PostGIS provides geospatial capabilities needed for locations, serviceability, proximity, and map-related data.
  • Cost Management owns configurable fuel/transportation-cost calculations. Billing / Payments owns transportation-fee collection, installments, payment transactions, and outstanding balances. A calculated operational cost is not assumed to equal the fee charged to a parent.
  • Provider-specific details remain in Infrastructure behind inward-facing abstractions for maps, WhatsApp, payments, school-system APIs, attendance devices, notifications, and storage.
  • Deterministic rules and solver logic own transportation feasibility, capacity, scheduling conflicts, route validity, cost-calculation methods, and configured business decisions. AI, if introduced later, remains an assistant layer.
Business alignment. The BRD requires pre-registration feasibility, seat availability and pricing; configurable route planning; multiple trips per bus per shift; supervisor review; live tracking; attendance; ETA updates; configurable fuel-cost calculation; online payments/installments; configurable operational reporting; and external integrations. This architecture separates those responsibilities so they can evolve without fighting each other.
Operational resilience. The BRD does not explicitly define offline mobile behavior. This architecture adds degraded/offline operation for the Driver and Bus Attendant experience as a production-readiness requirement: the active trip remains usable, operational events are durably queued on-device, and synchronization is explicit when connectivity returns.

4. High-Level System Architecture

The API remains the primary transactional entry point. The Worker hosts long-running Planning use cases and outbox processing through the same Application/Infrastructure contracts used by the API; it does not bypass module ownership. Driver/Attendant mobile keeps only the minimum active-trip data needed for degraded/offline operation and synchronizes queued operations through the API when connectivity returns. External provider calls and inbound callbacks are handled only through Infrastructure adapters.

7. CQRS, Mediator, Repositories, and Validation

The Application layer uses pragmatic CQRS. Commands express state-changing use cases, load aggregates through domain-specific repositories, enforce domain invariants, and commit through one IUnitOfWork. Queries use read-specific services/projections and may project directly with AsNoTracking. FluentValidation validates request/application input in the mediator pipeline; it does not replace aggregate invariants.

Concern Recommended approach
Commands Intent-oriented commands such as RegisterTransportation, GeneratePlan, ApprovePlan, StartTrip, MarkStudentAbsent.
Queries Read-specific projections through query-side abstractions; use AsNoTracking/direct DTO projection when aggregate behavior is not required.
Mediator MediatR routes commands, queries, domain-event notifications, and in-process integration-event handlers. API/Worker remain transport/composition hosts.
Repositories Domain-specific command repositories track aggregates only. They do not call SaveChanges and should not become a generic IRepository<TEntity> wrapper around DbSet.
EF Core EF Core is the persistence engine. A thin IUnitOfWork wrapper dispatches domain events, lets handlers track outbox/related changes, then performs one SaveChanges transaction.
FluentValidation Request/application validation such as required fields, ranges, input shape, and command-level validation. Runs through a MediatR pipeline behavior.
Domain invariants Rules that must always hold regardless of caller: capacity, valid state transitions, overlap validity, approval constraints, etc.

8. Domain Events and Event Handlers

Domain events are framework-free, past-tense facts raised by aggregates after their invariants are satisfied. Infrastructure adapts IDomainEvent instances to MediatR notifications so Application event handlers can react without coupling Domain to MediatR. A durable cross-module or external reaction is translated into a separate Integration Event and persisted to the transactional outbox.

Event example Possible reactions
StudentLocationChanged Recheck feasibility; mark affected draft planning inputs stale; audit the change.
TransportationRegistrationConfirmed Make the student eligible for future planning; update reporting projections.
PlanningRunCompleted Expose the plan for supervisor review; update planning status/notifications.
PlanApproved Create operational trip definitions; enqueue a durable integration event when required.
StudentAbsentForSession Make the stop skippable for that session; recalculate ETA; notify relevant users.
StudentBoarded / StudentExited Update attendance and parent-facing transport status.
PaymentReceived Update balance/installment projection and receipt workflow.
Event rule
Domain events announce successful domain facts; aggregate invariants are enforced before the event is raised. Domain events remain framework-free. The infrastructure dispatcher adapts them to MediatR application handlers. Durable integration events are separate contracts persisted through the transactional outbox.

Command transaction sequence: the handler changes aggregate state → the aggregate raises domain event(s) → IUnitOfWork dispatches those events → Application event handlers may add further tracked changes and/or OutboxMessage records → one EF Core SaveChanges commits the complete command transaction. Domain events themselves are not published externally.

9. Planning Engine Architecture

The Planning module is the core transportation-optimization capability. It builds a versioned PlanningRun from validated registration, fleet, policy and travel-time inputs; evaluates hard/soft/human-overridable constraints; assigns students to feasible trip candidates; sequences stops; schedules multiple waves against bus/driver/attendant calendars; validates the result; and records violations, metrics and unassigned reasons without silently waiving rules.

9.1 Planning inputs

  • Eligible registered students and their precise home locations.

  • Morning/afternoon requested session and current transportation status.

  • Bus capacity, availability, capabilities, and configurable school rules.

  • Driver/attendant availability and assignment restrictions.

  • School location, arrival deadline, operational buffer, and turnaround time.

  • Maximum student ride duration and other configured planning limits.

  • Routing/travel-time matrix from the selected map/routing provider.

  • Optimization mode and objective weights, such as travel time and/or fuel-related cost.

9.2 Constraint classification

Type Examples System behavior
Hard Bus capacity; impossible resource overlap; unserviceable location; invalid shift/resource availability. Solver must not generate an automatically approved solution that violates these constraints.
Soft Lower distance, lower travel time, balanced fleet usage, fewer vehicles, lower cost. Solver may trade these objectives according to configured weights.
Human-overridable Maximum ride time or selected policy limits under exceptional circumstances. System flags violation; supervisor must explicitly approve with reason. The solver does not silently waive the rule.

9.3 Multi-wave scheduling

A bus is not modeled as having a single route. It has a daily resource schedule containing one or more trips per shift. The scheduler must answer which bus performs each trip, in what order, and when each wave must begin.

Backward scheduling example
If the school target arrival is 07:35, Wave 2 requires 32 minutes, turnaround is 8 minutes, and Wave 1 requires 38 minutes, then Wave 2 must begin by 07:03, Wave 1 must finish by 06:55, and the bus must begin Wave 1 by approximately 06:17. Detailed models must also include where the bus physically ends one wave and starts the next.

9.4 PlanningRun aggregate

  • InputSnapshot - students/resources/settings used for the run.

  • ConfigurationSnapshot - constraints and objective configuration as of generation time.

  • SolverVersion - identifies the planning algorithm/version used.

  • GeneratedPlan - bus schedules, trips, stop sequences, assignments, times.

  • UnassignedStudents - students that could not be feasibly assigned, with reasons.

  • Violations/Warnings - hard, soft, and overridable findings.

  • Metrics - distance, expected travel time, fleet utilization, objective score.

  • Status - Draft, Running, Completed, Failed, UnderReview, Approved, Rejected, Superseded.

  • Revision history - supervisor edits create a new revision rather than destroying the original solver result.

9.5 Planning job execution

  1. API validates request and creates a durable PlanningRun in Pending/Queued state.

  2. Planning Worker claims the job and records Started/Running state.

  3. Worker builds a deterministic input snapshot and obtains the required distance/time matrix.

  4. Constraint engine validates inputs and classifies impossible assignments.

  5. Assignment, route optimization, and fleet scheduling produce a candidate plan.

  6. Final feasibility validation checks the complete plan independently of solver objective score.

  7. Plan, metrics, warnings, and unassigned reasons are persisted atomically.

  8. PlanningRunCompleted domain event is raised; the supervisor can review and revise the result.

11. Student Session Status and Attendance

Morning and afternoon are modeled independently. A single Student.IsAbsent flag is insufficient because the same student may use the bus in one session and alternative transportation in the other. Attendance is modeled as an operational fact; device/network transport concerns stay outside the domain model.

Entity / eventKey fields
StudentTransportationStatusStudentId, Date, Session, Status (Expected / Absent / AlternativeTransport / Cancelled), Source, UpdatedBy.
AttendanceEventEventId, StudentId, TripExecutionId, Session, EventType (Boarded / Exited), OccurredAt, Location, Source, DeviceId.
  • Attendance hardware is not allowed to shape the domain model. Bluetooth/NFC/device-specific protocols remain Infrastructure concerns.
  • Supported attendance sources can include BluetoothDevice, DriverApp, AttendantApp, ManualCorrection, or Import.
  • EventId is created at the event source so retries can be idempotent. The server records receipt/synchronization metadata separately from the attendance fact.
  • Device integration remains deferred until hardware/protocol validation, while the domain stays ready to ingest normalized events.

12. Real-Time Tracking and ETA

  • Driver/vehicle device sends BusId, TripExecutionId, coordinates, timestamp, and optional heading/speed.
  • Tracking owns the latest operational position and selected history according to the retention policy.
  • SignalR distributes relevant live updates to the Transportation Supervisor experience; durable state remains in PostgreSQL.
  • Parent ETA is derived from current position, remaining operational stop sequence, travel-time information, and session-specific changes such as skipped stops.
  • The Tracking module may consume planned/operational trip data through contracts/read models; it does not mutate PlanningRun or TripPlan artifacts.
  • At the reference scale, a dedicated streaming platform such as Kafka is not required initially.
  • When connectivity is lost, the device may buffer selected GPS samples for later history synchronization, but the server cannot represent them as live data while disconnected.
  • Supervisor and Parent experiences must expose freshness. A stale position is labeled with its last-update time; after a configurable freshness threshold, live location/ETA is shown as temporarily unavailable rather than pretending a stale point is current.
Offline tracking rule. Attendance can be captured offline and synchronized later; real-time tracking cannot. Buffered GPS points recover history after reconnection, not the lost real-time view. Offline turn-by-turn navigation depends on the selected map-provider/device capability and remains an open decision.

14. Persistence and Transaction Strategy

One PostgreSQL/PostGIS database is used per school deployment. Module ownership remains logical even when modules share the same physical database. Commands and queries intentionally use different persistence paths.

  • PostGIS is enabled for geospatial data and queries; spatial details remain Infrastructure concerns unless represented by domain value objects.
  • Use optimistic concurrency on aggregates where simultaneous administrative edits could cause lost updates.
  • Cross-module reads should use explicit contracts/read projections; cross-module writes should use the owning module's Application use case rather than another module's repository/DbSet.
  • Durable integration events are persisted as OutboxMessage records in the same transaction as the business mutation that caused them.

15. Transactional Outbox

The outbox closes the consistency gap between a committed business change and a durable cross-module/external reaction. Domain events stay in-process. When a handler needs durable delivery, it translates the domain fact into an Integration Event and stores an OutboxMessage before the command transaction commits.

Reliability rule. The business mutation and its OutboxMessage commit together. Delivery happens after commit and may be attempted more than once; consumers therefore need an idempotency strategy. No message broker is required initially, and introducing one later does not change Domain aggregates.

16. Fuel Cost and Transportation Cost Management

The BRD defines a configurable fuel-cost calculator based on an Admin-entered fuel-cost input and applicable trip details. It explicitly describes three calculation approaches. The architecture therefore treats cost calculation as its own business capability rather than hiding it inside Billing / Payments.

Cost Management owns

  • Fuel-cost input/configuration used for calculation
  • Calculation method selection
  • Trip/student cost calculations and snapshots
  • Cost reporting data

Billing / Payments owns

  • Transportation fee charged
  • Payment gateway transactions
  • Installments and payment documents
  • Outstanding balance
Open business detail. The BRD does not specify the exact fuel-consumption model, unit interpretation/source of the fuel-cost input, or a formula that makes calculated fuel cost equal to the transportation price. Those remain detailed-design decisions. The implementation must preserve this distinction rather than inventing a relationship.

19. Security, Privacy and Regulatory Baseline

The system handles student identity, home location, trip association, boarding/exit history, vehicle movement context, parent/contact information and payment-related data. Security and privacy controls are therefore architecture requirements. The items below describe the technical baseline; final legal obligations, lawful bases and contractual roles require qualified legal/compliance confirmation before production.

AreaArchitecture baseline
Access and least privilegeRole- and purpose-based authorization for Super Admin, Admin, Transportation Supervisor, Driver, Attendant and Parent/Student. Drivers/attendants receive only assigned-trip operational data; parents receive only information appropriate to their own child. Do not expose other students' identities, home pins or route details without a defined need.
Data classificationStudent identity, home location, attendance, trip and movement information are protected personal data and are treated by this architecture as high-risk operational data because they relate to children and physical movement. Do not label all such data as statutory Sensitive Personal Data; that term is reserved for categories defined by applicable law, such as financial, health, biometric and other designated data.
AuditabilityAudit plan approvals/overrides, manual attendance corrections, cost configuration, payment administration, permission changes, sensitive report exports, consent/compliance records where applicable, and other critical actions.
Data minimization and retentionCollect, cache, report and disclose only what is required for the stated purpose. Tracking history, local mobile cache, report exports, provider payloads and backups require explicit retention/expiration rules. Data should not be retained merely because storage is available.
Mobile/offline storageUse encrypted local storage for the minimal active-trip snapshot and pending operations; use platform Keychain/Keystore for secrets. Define logout, expiry, device-loss and wipe behavior. Evaluate MDM controls for school-owned tablets where operationally appropriate.
Provider / disclosure boundaryMaps, WhatsApp, payment, push/notification, school-system and future AI providers are explicit data-processing boundaries. Minimize disclosed fields, authenticate webhooks, define processor/security obligations and assess data location/cross-border transfers before enabling a provider.

19.1 Jordan regulatory baseline

Jordan deployment baseline. Design to support compliance with Jordan Personal Data Protection Law No. 24 of 2023, effective 17 March 2024, together with regulations and instructions issued pursuant to it, including the Security, Technical and Organizational Measures Instructions of 2025. The law's definition of personal data includes information capable of identifying a person directly or indirectly, including data relating to places where the person exists.
  • Consent / guardian: where prior consent is the applicable legal basis, the law requires it to be explicit/authenticated, specific as to duration and purpose, and requested clearly. Article 5 also addresses consent by a parent/legal guardian for a person who lacks legal capacity. The product should be architecture-ready to retain evidence, purpose, policy/version, grant/withdrawal and timing without assuming consent is the only lawful basis for every processing activity.
  • DPO: Article 11 expressly includes processing data of persons who lack legal capacity, processing sensitive personal data, financial information, and transferring databases outside the Kingdom among cases relevant to appointment of a Data Protection Officer. Applicability and the school/vendor responsibilities must be confirmed before production.
  • DPIA: the 2025 security instructions require a Data Protection Impact Assessment in specified cases, including sensitive-personal-data processing or transfer outside Jordan, and when required by the Council. Independently of the legal trigger analysis, this architecture recommends a DPIA before production because the product combines children's home locations, transport schedules, attendance and movement context.
  • Transfers / residency: hosting region and third-party providers are compliance decisions as well as technical/commercial decisions. Cross-border transfer conditions, adequacy/permissions and processor contracts must be assessed before production.
  • Data-subject lifecycle: production design must support applicable access, correction, objection, consent withdrawal, erasure/anonymization, complaint, breach-notification and retention obligations.
No compliance claim by architecture alone. The document states a design baseline and production-readiness obligations. It must not state that a deployment “is compliant” until the actual school, vendor contracts, data flows, hosting region, policies and operational procedures are legally reviewed and implemented.

Primary regulatory references: Jordan Ministry of Digital Economy and Entrepreneurship — Personal Data Protection Law No. 24 of 2023; Security, Technical and Organizational Measures Instructions of 2025; Data Disclosure Regulation 2025; and the Ministry's DPIA guidance/forms. Legal/compliance teams should validate the current official Arabic text and any later regulations/instructions before production.

23. BRD v2 Traceability Notes

This architecture is derived from the supplied School Transportation Solution BRD Version 2. The following requirements materially shape the design:

  • Accurate student location capture and automated WhatsApp pin intake where technically feasible.
  • Pre-registration serviceability, seat availability, requested shift/session and applicable price presentation.
  • Route planning using configurable time/fuel objectives and constraints such as capacity, location, grade, gender and other Admin-configured criteria.
  • Multiple trips per bus per shift with non-overlapping bus/driver/attendant schedules and sufficient turnaround time.
  • Supervisor review/modification of generated plans before operational use.
  • Driver and Bus Attendant trip access, communication and attendance support.
  • Real-time bus tracking, operational communication and parent ETA updates.
  • Morning/afternoon session-specific transportation status and attendance/punch records.
  • A configurable fuel-cost calculator supporting: planned-trip attributable distance, direct/isolated distance, and shared/common-route allocation; Admin selects the applicable approach.
  • Online transportation-fee collection, successful-payment document, installments, payment records and outstanding balance.
  • Reports covering feasibility, trip schedules, movement, attendance/status, fuel/transportation costs, payments/installments, and relevant communications.
